## The Problem

When a property owner disputes an assessed value, the assessor's office has to produce a
review that holds up to scrutiny — a document that shows its work: comparable sales, a
regression indicator, market trend, cost approach, equity across similar properties.

The analysis existed, but it lived in a set of R scripts written by one analyst. That
made every report a manual run, made the institutional knowledge single-threaded, and
made it hard to defend a number six months later when nobody could reproduce exactly how
it was produced. The office needed the same rigor, on demand, from a parcel ID.

## The Approach

**Two layers, deliberately separated.**

The core deliverable is deterministic: parcel ID → pull the data → compute every exhibit
→ render tables and charts → PDF. No model in the loop, no API cost, batch-capable, and
identical every time you run it. That property is the whole point — an assessment review
that changes between runs is not defensible.

A second, optional layer takes the structured output and drafts the narrative sections
with a commercial LLM, leaving the result editable before it's merged into the final PDF.
Keeping it strictly downstream of the deterministic layer means the numbers are never
generated by a model — only described by one.

**The report is nine exhibits**, each its own module: property characteristics, location
and context maps, comparable sales analysis, a regression indicator, market conditions,
a prior-sale trend test, the cost approach, an equity indicator, and a statutory
inflation adjustment — rolled up into a supportability summary and a decision-tree
outcome.

## Engineering the Port

Two conventions did most of the work of making an R-to-Python port survivable.

**Rules became data, not control flow.** The original pipeline carried a long tail of
hand-coded record corrections and region-to-trend-area mappings tangled into the
transformation logic. Those moved out into lookup tables loaded at runtime. The
transformation code got dramatically shorter, and — more importantly — the domain
experts can now correct a mapping without touching Python.

**Every ported script had to prove itself.** A golden-file harness runs each module
against the same inputs as the original R script and requires the output to match row for
row. This is the part that made the port trustworthy: "I rewrote it and the numbers look
about right" is not a standard anyone can sign a valuation against.

The team worked branch-per-task with mandatory cross-review before merge — I reviewed my
counterpart's exhibits and she reviewed mine, which caught a meaningful number of subtle
transformation differences that the golden files alone would not have explained.

## What I Took From It

The interesting problem here wasn't modeling — it was **reproducibility as a
requirement**. When the output of your pipeline is a document someone defends in a
hearing, "the model is accurate" is table stakes; "we can show exactly how this number
was produced, and produce it again" is the actual deliverable. That reframing changed how
I structure analytical code generally: separate the deterministic core from anything
probabilistic, externalize the judgment calls, and test against a known-good baseline
rather than against your own expectations.
