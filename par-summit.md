## The Problem

When a property owner disputes an assessed value, the assessor's office has to produce a
review that holds up to scrutiny in front of a Board of Equalization — a document that
shows its work: comparable sales, a regression indicator, market trend, cost approach,
equity across similar properties, and any statutory value caps the property may qualify
for.

The analysis existed, but it lived in a set of R scripts written by one analyst. That
made every report a manual run, made the institutional knowledge single-threaded, and
made it hard to defend a number six months later when nobody could reproduce exactly how
it was produced. The office needed the same rigor, on demand, from a parcel ID — plus a
couple of exhibits the legacy pipeline didn't have at all.

## The System

**Two layers, deliberately separated.** The core deliverable is deterministic: parcel ID
→ pull the data → compute every exhibit → render tables and charts → PDF. No model in the
loop, no API cost, batch-capable, identical every time you run it — an assessment review
that changes between runs is not defensible. A second, optional layer takes the
structured output and drafts narrative sections with a commercial LLM, left editable
before merging into the final PDF, so the numbers are never generated by a model, only
described by one.

The report is nine exhibits, each its own module — property characteristics, location
and context maps, comparable sales analysis, a regression indicator, market conditions,
a prior-sale trend test, the cost approach, an equity indicator, and a statutory
inflation adjustment — rolled up into a supportability summary and a decision-tree
outcome. I owned the last two of those, plus contributed to the comparable-sales engine
underneath several of the others.

## What I Built

**Equity indicator.** This exhibit answers a different question than the rest of the
report: not "what is this property worth," but "is it assessed like its neighbors." My
first version of the ranking logic had a subtle circularity — it classified each peer
property as superior or inferior using the *same* per-square-foot metric the exhibit was
supposed to be testing for fairness, which meant it could never actually surface the
inequity it was built to find. I redesigned it so peers are ranked on physical
characteristics (size, age, quality, condition) independent of the dollar metric, and the
dollar metric is only measured across that fixed ranking afterward — the yardstick and
the thing being measured had to stay separate. I calibrated the exhibit's similarity
threshold against real worked examples from the domain expert rather than picking a
number by feel, and later found — while reviewing a related fix a teammate had shipped
elsewhere in the codebase — that this exhibit hadn't picked up the same correction, so a
subset of properties were being scored inconsistently. Fixed it and added a test to keep
the two paths in sync going forward.

**Statutory inflation-adjusted value.** A statutory provision caps how much a qualifying
property's assessed value can rise, tied to the county's own median value change by area
rather than a published inflation index — a calculation that existed only as logic
buried in a colleague's R script and had to be reverse-engineered and independently
verified. I rebuilt it in Python and validated it against a golden file: the exhibit
reproduces the county's own published figures to the decimal on all but a small, explained
handful of areas before I trusted it with real cases. Along the way, validation surfaced
a subtle formatting issue in a shared numeric field that would have silently produced
wrong results without ever throwing an error — exactly the class of failure a
row-for-row comparison catches and a quick smoke test would not. The eligibility side of
this exhibit needed two external data sources that hadn't been delivered yet, so I built
it to degrade honestly — report
"cannot determine eligibility" rather than guess — while wiring the logic to the exact
fields those sources would eventually provide. When they arrived weeks later, eligibility
determination activated with zero code changes.

**The comparable-sales engine.** Beyond my two exhibits, I contributed to the weighted
similarity engine several other exhibits reuse: reweighting how heavily sale recency
versus geographic proximity count when ranking comparable sales, at the domain expert's
request, and discovering that the geographic-proximity ranking had been fully built but
was never actually wired up end-to-end in production — the subject property was never
given a location to rank from, so the feature silently did nothing. I connected it and
verified it was engaging correctly against real parcel data.

## Engineering the Port

Two conventions did most of the work of making an R-to-Python port survivable across a
team of engineers working in parallel.

**Rules became data, not control flow.** The original pipeline carried a long tail of
hand-coded record corrections and mapping tables tangled into the transformation logic.
Those moved into lookup tables loaded at runtime — the transformation code got
dramatically shorter, and domain experts could correct a mapping without touching Python.

**Every ported calculation had to prove itself against a known-good baseline.**
Golden-file tests run each module against the same inputs as the original R script, or
against a number the county had already published, and require the output to match. That
standard — not "the numbers look about right" but "we can reproduce this exactly" — is
what caught the formatting issue described above before it reached a real case.

The team worked branch-per-task with mandatory cross-review before merge, which caught a
meaningful number of subtle transformation differences the golden files alone wouldn't
have explained.

## What I Took From It

The interesting problem here wasn't modeling — it was **reproducibility, and honesty
about what the data can't yet tell you.** When a pipeline's output is a document someone
defends in a hearing, "the model is usually right" is table stakes; "we can show exactly
how this number was produced, and say plainly when we don't have enough to produce one"
is the actual deliverable. That shows up twice in the work above: the equity indicator
had to stop conflating what it measured with what it ranked on, and the inflation exhibit
had to be built to say "I don't know yet" honestly rather than guess — and to start
telling the truth automatically the moment it had the data to do so.
